# AGENTS.md — Hawraa backend (Lesan)

Deno 2 + **Lesan** (`jsr:@hemedani/lesan`) + MongoDB. Conventions are inherited from the owner's
Pejvak / lesanSatek / ziwound / nejayat projects — **when in doubt, match those repos**, not generic
Deno habits. lesanSatek is the richest reference for framework mechanics; Pejvak is the closest
reference for the *problem shape* (offline-first client, append-heavy ingest, idempotent batched sync).

## 1. What this backend is

The server side of two product pillars:

1. **Activity tracking** — every reading *and* listening session the Android app records offline is
   durably stored here, per user, and readable back (history, streaks, coverage).
2. **Recitation management** — a curated catalogue of reciters and their audio *editions*
   (verse-by-verse / surah-by-surah / juz-by-juz), plus a **download manifest** act that lets the app
   fetch a chosen recitation for offline storage. The catalogue publishes verified URL templates and
   file coordinates; the audio normally lives upstream. The server *may* also hold its own copy in
   `uploads/recitation/` (see §5.4) — an optional mirror, never the source of truth.

**Hard scope rule (D2):** the server stores **activity, references and catalogue metadata — never the
sacred Quran text or a translation/commentary's content.** Text stays bundled on the device; a
translation or commentary is referred to by a stable *key* (`fa.ansarian`, `al-mizan`), never by
content.

*Amended 2026-11-15 (owner request: "a method on backend to download and setup Telavat audios").*
The rule used to read "…or audio bytes", and the mirror is a deliberate exception to that clause. It
is narrow on purpose: the mirror is a **cache of files the catalogue already points at**, written only
by an explicit command (`deno task audio-mirror`) or a token-guarded act, never committed to the repo,
never the only way to obtain a file, and never referenced by a manifest that could not fall back to
the upstream URL. Nothing about sacred text changed.

## 3. Hard rules

- Entry point is always `mod.ts`. Strict TypeScript, **no `any`**. `camelCase.ts` file names.
- Every act: **validator (`*.val.ts`) written before implementation (`*.fn.ts`)**, registered via
  `setAct` in the act's `mod.ts`; every domain setup registered in `src/mod.ts`; every model
  registered in `models/mod.ts` **and** instantiated in `mod.ts`.
- **Schema ≠ folder**: acts register under the real model they operate on (`schema: "readingSession"`),
  never a synthetic schema.
- **One-directional relations**: the child owns the relation with `relatedRelations`; Lesan creates
  the reverse. Never duplicate. Single relations are embedded — filter on `user._id`, never
  denormalise `userId` into pure fields.
- In `models/`, import mixins (e.g. `createUpdateAt`) from their own file, not via `@lib` — the
  barrel imports `mod.ts` and would create a cycle.
- Auth wire format: JWT in the **`token` header (no Bearer)**. Request body:
  `{ model, act, details: { set, get } }`. Response: `{ success, body }`.
- `clientId` (client-generated UUID) is the idempotency key for synced rows: unique sparse index,
  known ids filtered before insert. A retry must never duplicate.
- Timestamps are epoch **milliseconds** (numbers), durations epoch **seconds** (integers).
  `createUpdateAt` dates are server bookkeeping only.
- Never commit `declarations/` or `.env`. Keep `typeGeneration: true` — the mobile client consumes
  only the generated types.
- A model that may accumulate **thousands of rows per user** (coverage, sessions) must **not** declare
  a `relatedRelations` reverse array on `user`. Query it by filter (`"user._id": …`) instead; the
  reverse array would grow without bound and turn every insert into a rewrite of a huge document.

## 4. The Lesan framework — reference

This section is the authority for *how* to write code here. Every recipe below is a shape that
exists and works in this repo or in lesanSatek.

### 4.1 Boot sequence (`mod.ts`)

```ts
export const coreApp = lesan();
const client = await new MongoClient(MONGO_URI, { ignoreUndefined: true }).connect();
const db = client.db(DB_NAME);
coreApp.odm.setDb(db);

export const user = users();                 // instantiate EVERY model, in dependency order
export const readingSession = readingSessions();
await ensureIndexes(db);                     // extra/compound indexes (see 4.4)

export const { setAct } = coreApp.acts;
export const { selectStruct, getSchemas } = coreApp.schemas;
functionsSetup();                            // register every domain's acts

if (import.meta.main) {
  coreApp.runServer({ port, typeGeneration: true, playground, cors, staticPath });
}
```

`import.meta.main` guards `runServer`, so importing `mod.ts` from a model or an act does not start a
server. Acts and models import the instantiated model from `mod.ts` — that is the single wiring point.

### 4.2 Models

A model file exports three things: the pure field struct, the relations struct, and a factory.

```ts
import { coreApp } from "../mod.ts";
import { boolean, defaulted, number, optional, type RelationDataType, type RelationSortOrderType, string } from "lesan";
import { createUpdateAt } from "../utils/createUpdateAt.ts";
import { user_excludes } from "./excludes.ts";

export const thing_pure = {
  /** Client-generated UUID; the idempotency key for sync. Unique + sparse. */
  clientId: optional(string()),
  name: string(),
  count: defaulted(number(), 0),
  ...createUpdateAt,
};

export const thing_relations = {
  user: {
    schemaName: "user",
    type: "single" as RelationDataType,
    optional: false,
    excludes: user_excludes,
    relatedRelations: {
      things: { type: "multiple" as RelationDataType, limit: 50, sort: { field: "_id", order: "desc" as RelationSortOrderType } },
    },
  },
};

export const things = () =>
  coreApp.odm.newModel("thing", thing_pure, thing_relations, {
    createIndex: { indexSpec: { clientId: 1 }, options: { unique: true, sparse: true } },
  });
```

Field validators (from `lesan`, i.e. superstruct):

| Validator | Notes |
|---|---|
| `string()`, `number()`, `boolean()`, `date()` | required |
| `optional(x)` | may be absent; **absent ≠ null** (see `excludes` note below) |
| `defaulted(x, value \| () => value)` | filled by Lesan on insert |
| `nullable(x)` | may be explicitly `null` |
| `enums(["a", "b"])` | closed set — use it for every status/kind field |
| `array(x)`, `object({...})` | embedded arrays and embedded sub-documents |
| `objectIdValidation` | a reference id in `set` |
| `...createUpdateAt` | `createdAt` / `updatedAt` (server bookkeeping) |

**Embedded sub-documents vs relations.** A value that is *part of* the row (a preset's steps, a
session's event log, a settings snapshot) is an `object(...)` / `array(object(...))` **pure field**:
it must travel with the row, be immutable per version, and never be queried by reference. Anything
you need to look up, filter or join on is a **relation**.

**Relation rules**
- Declare a relation **only on the model that holds the foreign key** (the child), and add
  `relatedRelations` for the reverse. Lesan embeds a `single` relation as a sub-document and
  maintains the reverse array itself.
- A `single` relation is **embedded**: filtering on `"user._id"` is a plain index-able field match,
  and there is no join. Do not add a parallel `userId` pure field.
- A relation **without** `relatedRelations` is legitimate: it stores the embedded reference and
  nothing else. Use it for high-cardinality children (see §3 last rule).
- Deleting a child auto-cleans the parent's reverse array. Deleting a parent is **blocked** while a
  reverse array still references it; `hardCascade: true` deletes the children too. Delete leaves
  first; never rely on `hardCascade` for routine cleanup.

**`excludes`** removes fields from the *embedded copy* of a relation, so a parent document never
carries another model's internals (`createdAt`, `updatedAt`, `deviceInfo`…). Every relation pointing
at `user` passes `excludes: user_excludes`.

### 4.3 Acts

Three files per act:

```
src/<domain>/<actName>/mod.ts        # setAct registration
src/<domain>/<actName>/<act>.val.ts  # validator  (written FIRST)
src/<domain>/<actName>/<act>.fn.ts   # implementation
```

```ts
// mod.ts
export const addSetup = () =>
  coreApp.acts.setAct({
    schema: "thing",              // the real model
    actName: "add",
    validationRunType: "create",  // or "update"
    validator: addValidator(),
    preAct: [setTokens, setUser], // ordered; each may throw
    fn: addFn,
  });
```

- `validationRunType: "create"` runs the `create` half of the validator; `"update"` runs the update
  half. Both are declared in the same `object({ set, get })` validator.
- `preAct` is the auth chain. `setTokens` verifies the JWT into `context.user`; `setUser` loads the
  real user row (rejects `status: "deleted"`, defaults `role`/`status`). Acts that are public
  (`register`, `login`) omit both.
- An act with a side effect on another model still registers under **its own** schema; it imports
  the other model from `mod.ts` directly.

### 4.4 Indexes

`newModel` accepts exactly **one** index:

```ts
{ createIndex: { indexSpec: { clientId: 1 }, options: { unique: true, sparse: true } } }
```

Everything else — compound, multi-key, TTL — is created in `mod.ts` by `ensureIndexes(db)` using the
raw Mongo handle. This is deliberate: one explicit, greppable list beats an option Lesan cannot
express. Collection names are the model names **verbatim** (`readingSession`, `presetAyahProgress`).

```ts
await db.collection("presetAyahProgress").createIndex(
  { "user._id": 1, "preset._id": 1, globalAyah: 1 },
  { unique: true },
);
```

`createIndex` is idempotent, so `ensureIndexes` is safe on every boot.

### 4.5 Reading

```ts
// one row, embedded relations included
const row = await model.findOne({ filters: { _id: new ObjectId(id) }, projection });

// many rows, newest first
const rows = await model
  .aggregation({
    pipeline: [{ $match: { "user._id": userId } }, { $sort: { startedAt: -1 } }, { $skip }, { $limit }],
    projection,
  })
  .toArray();

// counts
const qty = await model.countDocument({ filter: { "user._id": userId } });
```

- `projection` is a Mongo projection object. A client sends `get`, and `selectStruct(schema, depth)`
  in the validator constrains it; `projectionOrPure(get, schema)` in `utils/projection.ts` falls back
  to all safe pure fields when the client sends `{}` (Mongo rejects an empty `$project`).
- **Never** trust a client-supplied filter for ownership: derive `user._id` from the context.

### 4.6 Writing

```ts
// insert, with relations
const inserted = await model.insertOne({
  doc: { ...fields, createdAt: new Date(), updatedAt: new Date() },
  relations: { user: { _ids: userId, relatedRelations: { things: true } } } as never,
  projection: { _id: 1 },
});

// update one, returning the new row
const updated = await model.findOneAndUpdate({
  filter: { _id: new ObjectId(id), "user._id": userId },
  update: { $set: { ...fields, updatedAt: new Date() } },
  projection: get,
});

// atomic counters / merge operators work the same way
await model.findOneAndUpdate({
  filter: { ... },
  update: { $max: { lastAt: at }, $inc: { plays: 1 }, $push: { events: { $each: [event], $slice: -200 } } },
});

// delete (leaves first; see 4.2)
await model.deleteOne({ filter: { _id }, hardCascade: hardCascade || false });
```

**Ownership is part of the filter, not a separate check.** Every user-scoped write filters on both
`_id` (or the natural key) **and** `"user._id": userId`, so a forged id cannot touch another user's
row and a miss is indistinguishable from "not yours". Never `findOne` then update by `_id` alone.

**`updatedAt` is written explicitly** in every `$set`; `createUpdateAt`'s default only applies on
insert.

### 4.7 Validators

```ts
export const addValidator = () =>
  object({
    set: object({
      ...model_pure,             // reuse the model struct — one source of truth
      relationId: objectIdValidation,
    }),
    get: optional(selectStruct("model", 2)),
  });
```

- `selectStruct(schema, depth)` is the *only* legal shape for `get`: it restricts the projection to
  that schema's fields, so a client cannot ask for arbitrary document paths.
- A `set` object for an update lists only the updatable fields; use `optional()` for each.
- Batched acts take `array(<elementStruct>)` with `defaulted(..., [])` so an empty batch is valid.
- `utils/pagination.ts` exports `{ page, limit, skip }`; reuse it instead of re-declaring.

### 4.8 Context & auth

```ts
const { user }: MyContext = coreApp.contextFns.getContextModel() as MyContext;
const userId = new ObjectId(user._id);
```

`MyContext` (`utils/context.ts`) is `LesanContenxt & { user: { _id: ObjectId } & Partial<UserPure> }`.
`setUser` loads only `_id, role, status, email, displayName` — read anything else you need from the DB.

Roles here are `user` / `admin`. There is no org/unit scoping (that is lesanSatek's world): ownership
is per user row, and `admin` is only used for catalogue maintenance.

### 4.9 Errors

`throwError(msg): never` from `@lib`. Lesan turns a thrown `Error` into
`{ success: false, body: { message } }`. Messages are **for developers**, not UI copy: the client
classifies the failure and retries or drops the row.

**One exception:** `register`, `login` and `me` are the only acts whose messages the UI actually
reads. The mobile form matches a few distinctive fragments (`"already exists"`, `"incorrect"`,
`"at least" … "character"`, `"look valid"`) and turns them into localised copy, falling back to a
generic sentence for anything else. That is a deliberate, documented coupling — see §5.5. **If you
reword one of those messages, the matching fragment in `AuthViewModel.errorOf` must change too**,
or the form will silently degrade to "something went wrong". The durable fix is a machine-readable
`code` beside `message` in the envelope; Lesan does not emit one today.

**Gotcha: Lesan rewrites every colon in a response string.** Its serialiser runs
`.replace(/,/g, ", ").replace(/:/g, ": ")` over string values, so `deno task audio-mirror` is fine
but `deno task audio:mirror` comes back as `deno task audio: mirror` — a command that cannot be
copy-pasted. Do not put a `:`-bearing command in an error message, and prefer task names without a
colon (`audio-mirror`, not `audio:mirror`). The same rewriting applies to any value you return, which
is one more reason messages are for developers rather than for display.

### 5.1 `preset.steps[]` — the pattern language

A preset is an ordered list of steps applied to **each ayah** of whatever range is being played:

| `kind` | Meaning | Uses |
|---|---|---|
| `ayah` | play the verse's audio | `repeat` (1–10), `speed`, `gapMs` |
| `translation` | speak the verse's translation | `textKey` (`fa.ansarian`, `fa.maleki`), `languageCode`, `gapMs` |
| `tafsir` | speak the verse's exegesis | `textKey` (`al-mizan`), `languageCode`, `gapMs` |
| `silence` | a deliberate pause | `gapMs` |

So *"verse → Ansarian → Maleki → al-Mizan"* is four steps; *"verse twice → Ansarian → verse again"*
is `[ayah ×2, translation(ansarian), ayah ×1]`. `autoAdvance` decides whether the next ayah follows
after the last step or playback stops. The pattern is **range-independent**: the same preset applies
to a page, a surah, a juz or a selection — which is why coverage can be tracked per preset over the
whole Quran.

Text is **never** stored here — only the `textKey`. A key the device has not bundled is skipped by
the client, not rejected by the server (the catalogue of available texts is a content concern).

### 5.2 Why coverage is a separate ledger

`presetAyahProgress` exists so "how much of the Quran have I covered with *this* preset" and "which
ayahs exactly" are both O(1)-ish queries: `countDocument` for the percentage, an indexed range read
for the detail. Sessions answer *when*; progress answers *what*. Merging the two would make the
percentage a scan over history and would lose coverage when history is pruned.

Merge is **monotonic** (`$max` on counters, `$min` on `firstAt`, `$max` on `lastAt`) so a retried
sync is idempotent and two devices converge instead of double-counting.

### 5.3 Why a preset session is one row

The owner's requirement: *"activity should be logged as history, but not a new entry every time the
user presses play or pause."* So a session row is created once (`start`) and every subsequent
play/pause/seek/step **updates** it: counters increment, `lastEventAt` moves, the range extends, and
the event is appended to a capped `events[]` array for forensic detail. `finalize` closes it. A new
row is only ever created when there is no open row — i.e. a genuinely new sitting.

### 5.4 The audio mirror (`src/recitationAudio/`, `tools/mirrorAudio.ts`)

The catalogue says *where* audio lives; the mirror records what **this server** has fetched, measured
and can hand out itself. It exists for three reasons, in order of importance:

1. **An exact size.** A manifest built from a URL template cannot say how many bytes a file is. The
   mirror measures it on disk, so the device can tell a finished download from a truncated one.
2. **A second origin.** When upstream is unreachable, the LAN still works — which is what makes
   testing on a phone possible at all.
3. **Evidence.** `sha256` + `fetchedAt` turn "we have this file" into a claim with a record.

```sh
deno task audio-mirror --edition=parhizgar-murattal-ayah-48 --scope=surah:1
deno task audio-mirror --edition=shakernejad-tartil-juz-24   --scope=juz:1
deno task audio-mirror --edition=… --scope=surah:2 --limit=10 --dry-run
```

Scope syntax is `surah:N`, `juz:N`, `ayah:S:A`, `range:S:A-S:A` — parsed strictly by `scope.ts`,
because a typo that fell back to "everything" would start a 6236-file download.

**Invariants.** These are the four things a future edit must not break, each covered by
`mirror_test.ts` against a real HTTP server and a temp directory:

- Written to `name.mp3.part`, renamed to `name.mp3` only after the whole body lands. A file that
  exists is a file that finished.
- The first bytes are checked for an ID3 tag or an MPEG frame sync. A CDN error page answers `200`,
  so a status code proves nothing.
- A `.part` is resumed with `Range`. A `200` answer truncates and restarts; a `206` is only appended
  when `Content-Range` (if present) starts where we asked. Appending a whole body onto a half file
  yields a file of exactly the wrong length that plays as garbage.
- `bytes` comes from `stat` after the write, never from a header.

**Paths must agree.** The root is `${Deno.cwd()}/uploads/recitation` and the public path is
`/uploads/recitation/<relativePath>` — the same string the device uses as its own storage path.
`staticPath: ["/uploads"]` and Lesan's `${cwd}${url.pathname}` handler are the other two places that
have to agree. That is why `audioRoot()` follows the working directory instead of taking an env
override, and why `deno task start` must run from `back/`.

**`--watch-exclude=uploads` is load-bearing.** `deno run --watch` watches the working directory, not
just the module graph (which is also why `declarations` is excluded). Without the second exclusion,
mirroring audio restarts the server once per file — a loop that looks like the mirror crashing.

**What the manifest gains.** `getDownloadManifest` adds two fields per file, and only for files that
are `stored`: `bytes` (measured) and `mirrorPath` (server-relative, e.g. `/uploads/recitation/…`).
The client resolves `mirrorPath` against the origin it already knows, so nothing in the response is
absolute and the same manifest is correct from the LAN, loopback or a tunnel.

**Granularity is honoured literally, not degraded.** A `juz` edition asked for `range:1:1-2:29`
returns **one whole-juz file** (`juz:1`), because a 70-minute MP3 has no smaller part. Expanding a
per-ayah request down to the edition's granularity would make the device believe it holds 36 verses
when it holds a juz. `REQUIRED_PLACEHOLDER` is the gate: `{ayah}` for `ayah`, `{surah}`/`{surah3}`
for `surah`, `{juz}`/`{juz2}` for `juz` — a template missing its placeholder is a seed error, not a
runtime fallback. The client's half of this contract is `ReciterGranularity` (mobile `AGENTS.md`).

**Known upstream limitation.** Lesan's static handler builds its response with
`{...fileResponse.headers}`, which is a no-op on a `Headers` instance — so `Content-Length`,
`Content-Range` and `Accept-Ranges` are dropped and audio is served `chunked`. Ranges still *work*
(`curl -H 'Range: bytes=60000-'` returns exactly the remainder), but a client cannot verify the
resume offset and cannot see the length. That is precisely why `bytes` is in the manifest and why the
device checks the finished file against it. If the dependency is ever forked, the fix is one line:
`new Headers(fileResponse.headers)`.

**What is mirrored today** (2026-11-15, verified against a live probe on a spare port):

| Edition | Scope | Files | Bytes |
|---|---|---|---|
| `parhizgar-murattal-ayah-48` | `range:1:1-2:29` | 36 stored (29 fetched, 7 already present) | 4,474,501 |
| `shakernejad-tartil-juz-24` | `juz:1` | 1 | 12,651,123 |

The first five mushaf pages — 1:1–1:7, 2:1–2:5, 2:6–2:16, 2:17–2:24, 2:25–2:29, **36 ayahs** — all
fall inside juz 1, so for a juz edition "the first five pages" and "juz 1" are literally the same
download. The probe confirmed it: `range 1:1-2:29` → `ayahCount 36, fileCount 36,
mirroredFileCount 36`; `juz 1` → `ayahCount 148, fileCount 1`; and both files served `200` with
exactly the byte counts above.

**The upstream certificate for `dl.meshkatsound.com` is expired** (`notAfter` 2026-11-13 14:10:31
GMT). The payload itself is genuine — `audio/mpeg`, `content-length: 12651123` — so the mirror was
run with `--unsafely-ignore-certificate-errors=dl.meshkatsound.com`: **scoped to that host, never
globally**. A future re-mirror of Shakernejad will fail the same way until upstream renews; check the
bytes before concluding the mirror is broken, and do not "fix" it by disabling verification for every
host.

**Two acts, deliberately asymmetric.** `getAudioMirrorStatus` is public: it answers a question about
the server, and it is the one call worth being able to `curl` while a phone misbehaves.
`prepareAudio` writes to disk on request, so it is **disabled unless `ADMIN_TOKEN` is set**, requires
that token in `x-admin-token`, and refuses scopes above 60 files — the bulk path is the command, not
the endpoint.

### 5.5 Accounts (`src/users/`, `utils/password.ts`)

Three public acts and one authenticated one:

| Act | `set` | `get` | Answers |
|---|---|---|---|
| `user/register` | `email`, `password`, `displayName?` | `{ token, user }` | creates the account **and signs it in** |
| `user/login` | `email`, `password` | `{ token, user }` | same shape, so a client decodes one DTO for both |
| `user/me` | — | `{ user }` | "is this token still good, and whose is it?" |
| `user/registerDevice` | `deviceId` | `{ token }` | **legacy** anonymous device row; kept so old clients do not 500 |

**Why a gate exists at all.** The app is offline-first, but history written before anyone is signed
in belongs to nobody — it either gets attributed to the wrong account or has to be thrown away. So
the client refuses to run until an account exists, and everything after that stays offline-first
(the session is cached and the app opens with no connection).

**Password storage.** PBKDF2-HMAC-SHA256, 210 000 iterations (OWASP 2023), a 16-byte random salt per
row, and the iteration count stored **with** each hash (`passwordIterations`) so the cost can be
raised later without invalidating old rows. Verification is constant-time. The password is never
logged, echoed, or included in a response.

**The email is normalised before it is stored** (`trim` + lowercase). `Ali@x.com` and `ali@x.com`
are one person, and the unique index can only enforce that if the stored value is already folded. The
index is `{ unique: true, sparse: true }` on `email` — sparse because legacy device rows have none,
and Mongo treats every missing value as the same `null`.

**`deviceId` stopped being unique.** Two accounts signing in on one phone would collide on it. The
model's own `createIndex` therefore moved to `email`; `ensureIndexes.ensureUniqueSparse` drops and
recreates `deviceId_1` as sparse. Order matters: **Lesan creates the model index during `newModel`,
before `ensureIndexes` runs**, so a changed index declared in `newModel` aborts boot with
"an existing index has the same name as the requested index". A new field is safe there; a *changed*
one is not.

**Every credential failure answers the same sentence** — `email or password is incorrect`, for an
unknown address and a wrong password alike. Different sentences turn the login form into an oracle
that says which addresses are registered, which for an app whose users are identifiable by name is
information about the person rather than about the system. The status check (`deleted` / `suspended`)
runs *after* the password, so it cannot be used to probe either.

**`me` is the only act that may sign a client out**, and the distinction it must preserve is
"the server answered and refused" versus "we could not ask". Both arrive at the client as failures;
only the first is a `LesanException` (Lesan answered `success: false`), and the mobile repository
signs out on that alone. A network failure keeps the cached session, or a reader in a lift would be
ejected from a working app.

## 6. Idempotency & merge contracts

| Row | Key | Rule |
|---|---|---|
| `readingSession` | `clientId` | server filters known ids before insert; unique sparse index is the backstop |
| `preset` | `clientId` | last-write-wins on `updatedAtMs`; server never overwrites a newer local edit |
| `presetSession` | `clientId` | insert-if-absent; events merge by `clientId`, never by count |
| `presetAyahProgress` | (`user`,`preset`,`globalAyah`) | monotonic `$max`/`$min` merge; deltas are **absolute** values, not increments |
| `presetSession.events[]` | capped at 200 | `$push` + `$slice: -200`; the oldest detail is dropped, the counters remain exact |

**A retried request must produce the same state as a single request.** If a new field cannot be
merged that way, it does not belong on the wire.

## 8. Commands

```sh
deno task dev        # watch mode, playground at http://localhost:1407/playground
deno check mod.ts    # type check
deno lint && deno fmt --check
deno test --allow-all content/ src/   # reference tables + the mirror engine
deno task seed       # upsert the recitation catalogue (idempotent)
deno task audio-mirror --edition=<key> --scope=surah:1   # see §5.4
```

MongoDB must be running locally (`mongodb://127.0.0.1:27017/`, db `hawraa`) or set `MONGO_URI`.
Env vars: `MONGO_URI`, `DB_NAME`, `APP_PORT` (default 1407), `ENV`, `TOKEN_KEY`, `ADMIN_TOKEN`
(enables `prepareAudio`; unset = the act refuses) — see `.env.example`.

`deno task start` prints the **private LAN URLs** alongside the localhost banner (`utils/networkBanner.ts`).
That is the address a physical phone needs; it is filtered to RFC1918 so a VPN's `utun` address cannot
be mistaken for it. The mobile side reads it from `mobile/android/local.properties`
(`hawraa.baseUrl=http://192.168.1.111:1407`, no `/lesan` suffix).
